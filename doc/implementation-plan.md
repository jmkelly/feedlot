# Feedlot — Implementation Plan

> *A blog feed reader that chews up articles and spits out summaries.*

**Stack:** Go + Chi + Templ + HTMX + Tailwind CSS + SQLite  
**Goal:** A single-binary, self-hosted RSS/Atom reader with AI-powered summarization.

---

## 1. Architecture Overview

```
┌──────────────────────────────────────────────────────────┐
│                       Feedlot                             │
│  ┌──────────┐   ┌──────────┐   ┌──────────────────────┐  │
│  │  Handler  │──▶│  Auth    │──▶│    DB (SQLite)       │  │
│  │  (Chi)    │   │  (JWT)   │   │  ┌────────────────┐  │  │
│  └────┬─────┘   └──────────┘   │  │ users          │  │  │
│       │                        │  │ sessions       │  │  │
│       ├────────────────────────│  │ feeds          │  │  │
│       │                        │  │ articles       │  │  │
│  ┌────▼─────┐   ┌──────────┐   │  └────────────────┘  │  │
│  │  Feeds    │──▶│   AI     │   └──────────────────────┘  │
│  │  (gofeed) │   │  (LLM)   │                             │
│  └──────────┘   └──────────┘                             │
│                                                           │
│  Static Assets: /static/css/*, /static/js/*               │
│  Templates: Templ *.templ files                           │
└──────────────────────────────────────────────────────────┘
```

### Data Flow

1. **Feed Polling** (manual trigger or periodic): Fetch RSS/Atom → parse → store articles
2. **AI Summarization** (on ingest): For each new article → call LLM → store summary
3. **User Browsing**: View feeds → toggle read/unread → scan summaries
4. **Auth**: Email/password → JWT cookie → protected routes

### Phase 2: Application Core

#### 2.1. Main entry point & router (`main.go`)

- Chi router setup
- CORS middleware
- Static file server (`/static/*`)
- Route registration:
  - `GET /login` — login page
  - `POST /login` — login action
  - `GET /register` — register page
  - `POST /register` — register action
  - `POST /logout` — logout
  - `GET /` — dashboard (feed list + articles) [auth required]
  - `GET /feeds` — list feeds [auth required]
  - `POST /feeds` — add feed [auth required]
  - `DELETE /feeds/{id}` — remove feed [auth required]
  - `POST /feeds/{id}/refresh` — trigger refresh [auth required]
  - `GET /articles/{id}/toggle` — toggle read/unread [auth required]
  - `GET /settings` — settings page [auth required]
  - `POST /settings` — save settings [auth required]
- HTTPS server startup (configurable port)

#### 2.2. Auth middleware (`internal/handler/middleware.go`)

- Extract JWT from cookie (`feedlot_token`)
- Validate token
- Set `user_id` in request context
- Redirect to `/login` if unauthenticated
- Optional: CSRF protection middleware

#### 2.3. Auth handlers (`internal/handler/auth.go`)

- `GET /register` — render registration form
- `POST /register` — validate email + password, hash password, create user, set session cookie, redirect to `/`
- `GET /login` — render login form
- `POST /login` — verify credentials, create session, set cookie, redirect to `/`
- `POST /logout` — clear session from DB, clear cookie, redirect to `/login`

#### 2.4. Settings handlers (`internal/handler/settings.go`)

- `GET /settings` — render settings form (pre-filled with current values)
- `POST /settings` — validate and save settings
- Settings model (new table or JSON column in users):
  - `ai_provider` — openai, anthropic, ollama, custom
  - `api_key` — encrypted or stored as env var reference
  - `model_name` — e.g., gpt-4o, claude-3-haiku, llama3
  - `base_url` — for custom endpoints
  - `summary_length` — short / medium / long
  - `summary_language` — english, original, etc.

#### 2.5. Feed fetcher (`internal/feeds/fetcher.go`)

- `FetchFeed(feedURL string) (*model.Feed, []model.Article, error)` — uses gofeed
- Parses RSS 2.0, Atom, JSON Feed
- Extracts: title, description, site URL, icon/favicon
- For each item: GUID, title, URL, author, content, published date
- Deduplication: skip articles whose GUID already exists in DB
- Returns feed metadata + new articles ready for storage

#### 2.6. AI summarizer (`internal/ai/summarizer.go`)

- OpenAI-compatible HTTP client
- `Summarize(provider, apiKey, baseURL, model, articleText, length string) (string, error)`
- System prompt: "Summarize the following article concisely. Return only the summary text."
- Configurable max tokens based on length setting
- Supports: OpenAI, Anthropic (via proxy), Ollama, any OpenAI-compatible endpoint
- Error handling: timeouts, rate limits, malformed responses
- Optional: retry with backoff

#### 2.7. Handler helpers (`internal/handler/feeds.go`, `articles.go`)

- `GET /feeds` — list user's subscribed feeds with unread counts
- `POST /feeds` — validate URL, fetch feed metadata, save to DB
- `DELETE /feeds/{id}` — remove feed and its articles
- `POST /feeds/{id}/refresh` — fetch new articles, run AI summarization
- `GET /` — show feed list + selected feed's articles (or all unread)
- `GET /articles/{id}/toggle` — flip is_read, return updated state (HTMX swap)

### Phase 4: Settings Persistence & AI Integration

#### 4.1. Settings table / model

Add to schema (migration 002):

```sql
CREATE TABLE IF NOT EXISTS user_settings (
    user_id INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    ai_provider TEXT DEFAULT 'openai',
    api_key_encrypted TEXT,
    model_name TEXT DEFAULT 'gpt-4o-mini',
    base_url TEXT,
    summary_length TEXT DEFAULT 'short',
    summary_language TEXT DEFAULT 'english',
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

#### 4.2. API key encryption

- Encrypt API keys at rest using a derived key from the user's password or a server-side master key
- Use AES-256-GCM with a random nonce per key
- Decrypt on read when making AI calls

#### 4.3. AI summarization pipeline

- After feed refresh, iterate over new articles
- For each article with content:
  1. Truncate content to max context length (e.g., 8000 chars)
  2. Call LLM with summarization prompt
  3. Store summary in `articles.summary`
- Handle failures gracefully (log error, continue)
- Optional: rate limiting per provider (e.g., 10 requests/min)

### Phase 5: Polish & DX

#### 5.1. Background feed polling

- Option A: HTMX-triggered polling (user visits dashboard → triggers refresh of each feed)
- Option B: Go ticker in a goroutine with configurable interval (every N minutes)
- Option C: Separate binary/CLI command for feed refresh

#### 5.2. Error handling & UX

- Graceful error pages for 400, 401, 404, 500
- Flash messages for success/error states
- Loading states (spinners) for feed refresh and AI summarization
- Empty states: "No feeds yet — add one to get started"

#### 5.3. Testing

| Package | Test strategy |
|---------|---------------|
| auth | Unit tests for hash/verify, token gen/validation |
| db | Integration tests with in-memory SQLite |
| feeds | Mock HTTP server for feed fixtures, test parsing |
| ai | Mock HTTP server for OpenAI-compatible endpoint |
| handler | httptest-based handler tests with test DB |
| templates | Snapshot or approval tests for rendered output |

#### 5.4. Configuration & deployment

- Config via environment variables:
  - `FEEDLOT_PORT` (default: 8080)
  - `FEEDLOT_DB_PATH` (default: `./feedlot.db`)
  - `FEEDLOT_JWT_SECRET` (required)
  - `FEEDLOT_ENCRYPTION_KEY` (for API key storage)
  - `FEEDLOT_POLL_INTERVAL` (default: 30m)
- Single binary build: `go build -o feedlot .`
- Systemd user service: `deploy/feedlot.service` — this is how Feedlot is actually deployed and run (see README "Run as a systemd service")

## 6. Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **Templ vs std html/template** | Templ | Type-safe templates, compile-time checked, Go-native |
| **HTMX vs JS framework** | HTMX | Server-rendered HTML, minimal JS, perfect for read/unread toggling |
| **SQLite vs Postgres** | SQLite | Zero-infrastructure, single binary, WAL mode for concurrency |
| **JWT vs session cookies** | Both | JWT for API, session tokens stored in DB for revocation |
| **AI provider abstraction** | OpenAI-compatible client | Works with OpenAI, Anthropic (via proxy), Ollama, LocalAI, etc. |
| **CSS approach** | Tailwind (utility-first) | Consistent design system, small output with purging |
